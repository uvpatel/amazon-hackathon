# Candidate Generation / Blocking Specification

## Goal

Blocking is not a cosmetic optimization. It determines the recall ceiling and is explicitly audited in the challenge.

For each Source 1 entity, generate a **small candidate set with high probability of containing every true match**.

The final candidate set must be exactly what the matching model scores.

## Design

Use multiple independent blocking rules and take their union, followed by a controlled final candidate filter.

```text
S1 record
  |
  +--> exact/near name index
  +--> character-name index
  +--> address-token index
  +--> postal/number tokens where present
  +--> country-compatible index
  |
  v
union candidates
  |
  v
candidate deduplication
  |
  v
cheap pair-level safety filters / top-K cap
  |
  v
FINAL candidate set
```

## Rule families

### B1 — normalized name exact

Index target records by a normalized business name.

Useful for:

- punctuation changes
- case changes
- legal suffix cleanup
- whitespace differences

### B2 — character n-gram name retrieval

Build character n-gram TF-IDF or equivalent sparse index over target names.

Retrieve top-k target records by cosine similarity.

This handles:

- typos
- transliteration variation
- abbreviations
- token concatenation

### B3 — token overlap

Use normalized name token sets and inverted token indexes.

Candidate records sharing rare/high-information tokens are retrieved.

Do not treat common tokens such as generic legal suffixes as strong evidence.

### B4 — address token retrieval

Index informative normalized address tokens.

Prioritize:

- postal/PIN-like tokens
- house/building numbers
- street numbers
- distinctive street/locality tokens

Do not require a complete address match.

### B5 — country-aware retrieval

Use the observed country string as a blocking feature where available, but do not enumerate or hard-code known countries.

If country is missing or inconsistent, retain fallback routes.

### B6 — cross-field fallback

For records with weak names, use address-driven retrieval; for weak addresses, use name-driven retrieval.

The goal is high recall without all-pairs comparison.

## Candidate reduction

The blocking design should be evaluated using:

- candidate recall / blocking recall
- average candidates per Source 1
- median candidates per Source 1
- p95 candidates per Source 1
- total candidate pairs
- reduction ratio

Definitions:

```text
candidate_recall =
  true matched pairs present in candidates /
  true matched pairs in ground truth

reduction_ratio =
  1 - (#candidate_pairs / #possible_pairs)
```

Possible pairs are:

```text
|S1| * (|S2| + |S3|)
```

## Important implementation rule

Do not write an early blocking output to `candidate_pairs.tsv` and then silently filter it later.

Instead:

```text
raw blocking
   -> candidate union
   -> final candidate pruning
   -> pair feature computation
   -> model inference
```

The candidate file must be written from the boundary immediately before model inference.

## Candidate caps

A cap may be necessary for pathological records, but it must be measured against validation recall.

Prefer adaptive caps:

- retain all high-confidence exact-name candidates
- retain top-k fuzzy-name candidates
- retain top-k address candidates
- retain candidates generated by rare-token rules
- then deduplicate

Avoid a blind global top-k that can discard true multi-match entities.

## Failure handling

If a record produces no candidates:

- keep it in `candidate_pairs.tsv` with an empty list
- final prediction must be empty
- log the count and sample IDs for diagnostics

## Training leakage warning

Blocking indexes for validation must be constructed from the appropriate training/reference partition. Do not use validation labels to tune candidate membership.
